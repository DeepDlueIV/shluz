# Shluz · контекст проекта

Обновлено: 2026-10-18. Этот файл — точка входа для следующего разработчика.
Фактические результаты проверок ищите в CI и `docs/telegram-acceptance.md`;
наличие кода не означает, что владелец уже проверил его в своём окружении.

## Цель и принятые решения

SaaS-доступ к нейросетевым моделям через центральный API-шлюз и несколько интерфейсов.
Владелец ориентируется на модели с менее строгими ограничениями; окончательный
поставщик, конкретные модели, условия их коммерческого использования и hosting не выбраны.
Cloud API и собственное оборудование остаются альтернативами. Telegram — первый
клиент для закрытой проверки. Desktop/harness и публичное демо — последующие этапы.

Один репозиторий, один планируемый сервер, отдельные процессы/контейнеры:
```text
telegram_bot/ ──HTTP──┐
web/ (план) ──HTTP───┼── app/ Shluz ── провайдер API / собственные модели
 desktop/ (план) ────┘       │
                         аккаунты, тарифы, лимиты, расход
                            │
                        /admin · база шлюза
```
База истории Telegram отдельна и недоступна gateway-коду. Бот не имеет ключей
поставщиков, admin/bootstrap-секрета или прямого доступа к БД шлюза.

## Реализовано в коде

- `app/`: существующий FastAPI gateway, OpenAI-подобные models/chat endpoints,
  mock и адаптер Venice; аккаунты, identities, личные токены, тарифы, подписки,
  квоты/резервы/учёт расходов, административная панель.
- Новые личные endpoints `/v1/me` и `/v1/me/telegram`: профиль и безопасная
  привязка Telegram через доверенный бот с персональной или короткой внутренней сессией.
- `telegram_bot/`: aiogram polling-клиент, автоматическое подключение по приглашению/заявке,
  короткие сессии от шлюза, локальный профиль, persistent SQLite история/диалоги,
  меню и inline-кнопки, модели, тариф/лимиты, стили, очистка/удаление/экспорт,
  статусы ожидания, длинные ответы, ошибки/отмена и защита от повторов.
- Owner review: привязанные к запросу кнопки отмены/файла/оценки; `/last`,
  подтверждаемый платный `/retry` с версиями ответа, `/rename`, `/forget`,
  поддержка и read-only агрегаты `python -m telegram_bot.report`.
  Навигация редактирует меню, не ответы. Исправлены остаточные заголовки после
  retention, немедленный лимит истории, общая длительность HTTP и размер JSON.
- `compose.owner.yaml`, `scripts/gateway_owner_check.py`: отдельная локальная
  приёмка gateway на mock, порт 18000, собственные env/том и скрытый ввод ключа.
- `compose.yaml`: gateway по умолчанию; бот подключается профилем `telegram`,
  отдельными `.env.telegram` и томом; служебный доступ создаётся автоматически.
  Старый JSON опционален только для миграции. Gateway-only запуск сохранён.
- `web/`, `desktop/`: только README-заготовки, не работающие приложения.

## Технологии и расположение

Python >=3.12; FastAPI/SQLAlchemy/Alembic/httpx, aiogram >=3.31,<4.
SQLite локально; существующий gateway допускает PostgreSQL. История бота использует
отдельную SQLite, один процесс, схему user_version=2 с миграцией v1 → v2. Настройки и тестовые defaults:
`.env.telegram.example`. Секреты и базы исключены из Git и Docker build context.

Тесты шлюза: `tests/`; новые API: `tests/api/test_my_account.py`;
бот: `tests/telegram/`. Запуск: `ruff check .`, `pytest -q`.
CI проверяет также миграции, контейнер и HTTP интеграцию. Настоящий Telegram и
платные модели не считаются проверенными без отдельного живого запуска с секретами.

## Важные ограничения, не скрывать

Текущий gateway выбирает активный тариф и квоты **на аккаунт**, а не на канал.
Telegram и desktop могут получить разные тарифы в будущем. Бот не копирует биллинг:
получает `scope:account` через API и честно показывает общую квоту. Изменение этих
правил — отдельная миграция/задача gateway, а не скрытое изменение текущих подписок.

Регистрация закрытая: приглашение с тарифом автоматически создаёт аккаунт и привязку;
без приглашения создаётся заявка для одобрения. Никакого публичного бесплатного
доступа к платным моделям или продажи подписок. Ключи на пользователей вручную не выдаются.
Тексты истории хранятся без шифрования приложением; retention/удаление описаны в README.
POST генерации автоматически не повторяется. Exactly-once, отмена расхода и отмена
на стороне провайдера не гарантируются. Нет настоящего streaming; UI статуса отдельно.

Старая ветка `feat/telegram-closed-beta` содержит другой незавершённый набросок в
`apps/telegram-bot/`. Она не источник этой реализации и не должна слепо объединяться
с `telegram_bot/`. Код текущего этапа расположен только в `telegram_bot/`.

## Панель и правила работы — 18.10.2026

Техническую приёмку самостоятельно проводит агент/разработчик в изолированной среде и CI.
Владелец оценивает интерфейс и вводит свои секреты у себя. Не повторять обычные терминальные
проверки с владельцем и не останавливаться для промежуточных отчётов. Он сообщил об успешной
проверке локального mock-пути, квот, независимости аккаунтов, отзыва ключа и перезапуска.
Это не утверждение о готовности production или реального провайдера.

Конфигурация owner-check по умолчанию использует SQLite в Docker-томе owner_data, не Supabase.
Приватный файл .env.owner владельца агент не читает. Теперь обзор показывает тип базы из
настроек работающего шлюза, без строки подключения. Данные в Supabase не переносились.

Панель: единая закреплённая шапка, русские подписи/даты, читаемые суммы с сохранением точности,
имена и ссылки на аккаунты в расходах (включая архив), поиск пользователей, раскрываемые
служебные данные, подсказки ? и необязательное название ключа. Финансовая логика не менялась.

tests/integration/test_owner_acceptance.py повторяет настоящий HTTP-сценарий и перезапуск
процесса с временной базой. ui_tests/ проверяет интерфейс в Chromium; CI сохраняет скриншоты
на вымышленных данных. Подключение Telegram для визуального просмотра описано в
[docs/telegram-first-look.md](docs/telegram-first-look.md), использует compose.owner.telegram.yaml.
Живой Telegram без пользовательского BotFather-токена не считается проверенным.


## Уточнение 2026-10-18: автоматическое подключение Telegram

Ручной JSON-список был техническим ограничением старой беты, не требованием владельца.
Владелец оценивает готовый UI. Создание аккаунта, привязка Telegram, служебная
авторизация, сохранение/обновление ключей и технические проверки — задачи приложения
и разработчика, а не владельца.

Текущий Compose включает автоматический режим: приглашение → Start → аккаунт и сессия;
без приглашения → заявка → одобрение в панели Telegram. Закрытый доступ сохранён.
Новые сессии 15 минут, разрешение проверяется в БД на каждом запросе. Служебный ключ
создаётся в отдельном Docker-томе автоматически. Прежние разрешения мигрируют из
опционального старого файла с сохранением аккаунта/тарифа/расхода/истории. Отзыв
импортированного ключа продолжает закрывать доступ; заблокированных автоматически не пускаем.
Таблицы шлюза добавлены миграцией 20261018_06; база бота по-прежнему версии 2.

Старые инструкции о ручной выдаче Telegram-токена/JSON на каждого пользователя
заменены [новым порядком](docs/telegram-auto-onboarding.md). Секреты и локальные правки
Codex не представлены в GitHub. Не считать публикацию в ветке установкой на компьютере.
