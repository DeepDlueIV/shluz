# Telegram · закрытая бета Shluz

Бот живёт в `telegram_bot/`, шлюз — в `app/`. Это два процесса в одном репозитории
и одном Docker Compose. Telegram не получает ключи поставщиков или доступ к базе шлюза.

## Запуск на сервере

Нужны Git, Docker Engine/Desktop с Compose **2.24+** и отдельный тестовый бот,
созданный через **@BotFather**. С реальными пользователями используйте защищённый сервер;
админ-панель шлюза не открывайте всему интернету. Сначала оставьте провайдер `mock`.

1. Если шлюз уже настроен, **не заменяйте его `.env` и не удаляйте Docker-том**.
   Для нового окружения скопируйте `.env.example` в `.env`, замените `CHANGE_ME`.
   Запустите только шлюз:
   ```sh
   docker compose up -d --build shluz
   ```
2. Скопируйте `.env.telegram.example` в `.env.telegram` и впишите токен BotFather
   в `TELEGRAM_BOT_TOKEN`. Остальные секреты шлюза в этот файл не переносите.
3. Создайте каталог `secrets` и скопируйте `telegram_bot/access.example.json`
   в `secrets/telegram-access.json`. Пустой `{}` означает, что доступ не выдан никому.
4. На Linux контейнер работает от UID **10001**. Дайте ему чтение файла доступа,
   не открывая секреты всем пользователям:
   ```sh
   chmod 700 secrets
   sudo chown 10001 secrets/telegram-access.json
   sudo chmod 600 secrets/telegram-access.json
   chmod 600 .env .env.telegram
   ```
   Docker Desktop на Windows управляет правами примонтированного файла отдельно;
   ограничьте чтение файла своей учётной записью. Файл должен существовать **до запуска**.
5. Запустите бота:
   ```sh
   docker compose --profile telegram up -d --build
   docker compose ps
   docker compose logs --tail=100 telegram_bot
   ```
   До подключения пользователей бот отвечает сообщением о закрытом тестировании.
   Он работает через long polling, поэтому отдельный публичный порт/HTTPS для него не нужен.
   Если уже настроен webhook, запуск останавливается: бот не удаляет чужую настройку.

### Подключение тестировщика

1. Человек открывает бота и отправляет `/start`. Бот показывает его Telegram ID.
2. На `/admin/plans` создайте тестовый тариф с ограничением запросов; на `/admin/users`
   создайте аккаунт, назначьте тариф и выпустите **отдельный персональный токен канала
   `telegram`**. Полный токен показывается один раз. Не используйте bootstrap/admin-токен.
3. В защищённом файле доступа сопоставьте ID и токен:
   ```json
   {
     "123456789": "shluz_REPLACE_WITH_PERSONAL_TOKEN_FROM_ADMIN"
   }
   ```
   Ключ в JSON — строка с числовым Telegram ID, не username. Разным ID нужны разные токены.
   Для нескольких тестировщиков добавляйте строки через запятую. Пример выше не даёт доступа сам по себе.
4. После изменения существующего файла доступа перезапуск бота не нужен. В контейнере
   используется файловый bind mount: редактируйте содержимое смонтированного файла, сохраняя
   inode, либо после атомарной замены/редакторского rename выполните:
   ```sh
   docker compose --profile telegram up -d --force-recreate telegram_bot
   ```
   Это важно и для отзыва доступа. При повреждённом JSON бот закрывает доступ всем, а не
   продолжает использовать старые разрешения. Для немедленного надёжного отзыва также
   отзовите персональный токен в админке шлюза.
5. Пользователь повторяет `/start`, затем отправляет обычный текст.
   Ответ `Shluz mock reply: ...` — тест интеграции, **не настоящая нейросеть**.

При первой успешной проверке токена бот создаёт локальный профиль и связывает
Telegram ID с существующим аккаунтом шлюза через `/v1/me/telegram`. Публичной
самостоятельной регистрации и бесплатного тарифа по умолчанию нет.
Перевыпуск токена того же аккаунта поддерживается. Перенос ID на другой аккаунт
намеренно блокируется: сначала администратор должен согласовать миграцию identity
и локального профиля, а не просто подменить строку с ключом.

## Что доступно

Главное меню: новый/текущий чат, модели, диалоги, тариф, лимиты, настройки, помощь.
Команды: `/start`, `/menu`, `/new`, `/models`, `/history`, `/plan`, `/profile`,
`/settings`, `/export`, `/clear`, `/delete`, `/cancel`, `/privacy`, `/help`.
Дополнительные алиасы: `/balance`, `/limits`.

Настройки: обычный/краткий/подробный стиль; очистка и удаление с подтверждением.
Модели берутся только из шлюза. У каждого пользователя свои диалоги; в запрос
уходят только законченные пары сообщений текущего диалога. Длинный контекст
сокращается с уведомлением, сохранённая история остаётся доступной через экспорт.
История не переносится автоматически между Telegram, сайтом и desktop.

Во время ответа отображаются typing и меняющийся статус с кнопкой отмены ожидания.
Длинный ответ делится по границам текста с учётом UTF-16; более шести частей
по умолчанию отправляются одним UTF-8 `.txt`, без обрезания.
Форматирование модели ограничено безопасным жирным текстом и блоками кода;
неподдержанный Markdown отображается текстом. Произвольный HTML экранируется.

### Тарифы, повторные запросы, отмена

Шлюз — единственный источник тарифа и квот. Кредиты — не денежный баланс.
**Сейчас квоты общие для аккаунта**, независимо от канала; интерфейс сообщает это.
Будущие разные тарифы Telegram/desktop потребуют расширения правил шлюза,
но не второй системы биллинга внутри бота.

Каждый Telegram update фиксируется в SQLite до обработки; генерация также
регистрируется до HTTP POST. Бот не повторяет генерацию автоматически при таймауте,
перезапуске, повторной доставке update или ошибке отправки результата.
При сбое между записью update и ответом сообщение может остаться без результата —
это сознательный выбор против двойного расхода, **не гарантия exactly-once**.
HTTP-заголовок X-Request-ID нужен для диагностики, не обеспечивает идемпотентность шлюза.
Отмена останавливает ожидание, но не гарантирует остановку модели или возврат расхода.
После ошибки доставки уже сохранённый ответ можно получить через `/export`.

## Настройки и данные

`TELEGRAM_MAX_PARALLEL_REQUESTS=4` ограничивает число одновременно ожидаемых ответов;
у каждого пользователя — не более одного. По умолчанию пауза между генерациями 2 секунды.
Бот рассчитан на **один экземпляр**. Блокировка защищает одну SQLite-базу от второго
процесса; она не защищает от запуска того же токена на другом сервере/другой базе.
Heartbeat проверяет работоспособность процесса/event loop, не качество ответа провайдера
и не доступность Telegram в каждый момент времени.

Данные бота: отдельный Docker-том `telegram_data`, SQLite с версией схемы 1.
Данные шлюза: существующий `shluz_data` или внешняя PostgreSQL.
Тексты диалогов хранятся **без шифрования на уровне приложения**; права каталога/файла
ограничены. Очистка старше 30 дней выполняется при запуске и примерно раз в час;
максимум 200 завершённых обменов в диалоге. Параметры можно уменьшить в `.env.telegram`.
Профили и названия диалогов автоматически по сроку не удаляются. Диалоги удаляются
пользователем. Резервные копии и сами сообщения в Telegram очищаются отдельно.
Содержимое чатов и полные ключи не пишутся в обычные логи. Для поддержки используются
типы ошибок и метаданные запросов; ключи редактируются фильтром логирования.

При резервном копировании живой SQLite учитывайте WAL: используйте SQLite backup API
или остановите бота перед копированием файла. Не удаляйте том для обычного обновления.
Не выполняйте `docker compose down -v`, если нужны текущие данные.

## Проверки без Telegram и провайдерских ключей

```sh
python -m pip install -e '.[dev]'
ruff check .
pytest -q
python -m telegram_bot --check
```

Последняя команда проверяет только формат настроек/закрытого списка, не валидность
токена на сервере Telegram. Она требует локальный `.env.telegram` и существующий
файл доступа. Для запуска без Docker укажите `TELEGRAM_GATEWAY_URL=http://127.0.0.1:8000`
и выполните `python -m telegram_bot` после запуска шлюза.
