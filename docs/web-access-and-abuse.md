# Гостевое демо и email OTP — реализованный серверный контракт

Версия: web-access-v1, 19.10.2026. Требования владельца: один пробный запрос без
регистрации на сайте; OTP вместо пароля; реальные потоковые ответы; лимиты в шлюзе.

## Что реализовано и что не включено

Модули `app/webaccess`, миграция `20261019_09`, общие предохранители в UsageService,
панель `/admin/web-access`. Тесты используют подменённые транспорт/почту только в
изолированном `environment=test`. В обычном запуске нет секретного «пропустить
CAPTCHA», кода из логов, фиксированного OTP или автоматической тестовой авторизации.

По умолчанию `SHLUZ_WEB_ENABLED=false`: публичный cookie API закрыт.
Реальные SMTP, Turnstile, HTTPS, доверенные reverse proxy и оплаченный Venice не
настроены этим коммитом. Перед открытием сайта необходим отдельный живой тест
доставки письма, проверки антибота, IP-цепочки и потоковой генерации. Платежи,
официальный Telegram Login браузера и frontend не входят в этот блок.

## Первый визит и API

Разместить frontend и API на одном origin через reverse proxy; допускаются также
точно разрешённые same-site origins. Cross-site cookies специально не поддержаны:
не ослаблять SameSite для случайного Vercel preview. Для preview использовать
проксирование `/v1/web` от frontend к gateway с корректной доверенной IP-цепочкой.

1. `POST /v1/web/session`, пустое тело или `{}`; заголовок `Origin` точный.
   Ответ: `csrf_token`, `authenticated`, `expires_at` (Unix), `captcha_sitekey`,
   `demo:{requests,max_input_chars,max_output_tokens}`. HttpOnly cookie
   `__Host-shluz_web`, Secure, SameSite=Strict, Path=/, без Domain. Сам токен cookie
   JavaScript не читает. Guest session 30 дней, подтверждённая сессия 7 дней;
   срок на сервере абсолютный. Посещение создаёт только сессию, не Account.
2. Для каждого POST дальше нужны cookie (`credentials:include`), тот же Origin,
   `X-CSRF-Token` из ответа, JSON Content-Type. CSRF хранить в памяти страницы.
3. Перед демо получить свежий Turnstile token для action `demo_chat`.
4. `POST /v1/web/chat/completions`:
   `{ "prompt":"вопрос", "request_id":"новый UUID", "turnstile_token":"…" }`.
   Сервер создаёт guest Account при первой подтверждённой попытке, назначает DemoGrant,
   выбирает разрешённую модель; клиент не передаёт system/messages/tools/max_tokens.
   Неизвестные поля отвергаются. Отправка `model` в демо запрещена.
   Ответ всегда SSE; читать POST через streaming fetch, не EventSource.
   `[DONE]` означает корректное окончание, EOF без него — обрыв. Не повторять POST
   автоматически; сетевое событие могло произойти после расхода провайдера.
5. `GET /v1/web/me` возвращает профиль и остаток. Без Account — guest-профиль;
   после использования — тот же профиль/allowance общего gateway. Повторный POST
   session, обновление страницы или смена месяца не пополняет выданный пакет.

Остальные cookie read routes: `GET /v1/web/models`, `/v1/web/plans`,
`/v1/web/me/usage?limit=20&offset=0`. Они используют тот же серверный учёт, что и
Bearer API. Чужие данные, prompt/ответы, upstream cost и ключи в них не включены.
`/me/usage` требует Account (после демо или подтверждения почты); гостю без Account
сайт пока не показывает историю расходов. `payment.enabled=false` сохраняется.

Минимальный web chat в этом блоке принимает один текстовый prompt, не историю/файлы.
Для подтверждённого аккаунта с действующей подпиской разрешён параметр `model`,
только из пересечения тарифа и web-канала. Cookie не даёт доступ к обычному Bearer
endpoint `/v1/chat/completions`, админке или внутреннему Telegram connector.

## OTP без пароля

`POST /v1/web/auth/otp/request`:
`{"email":"person@example.org","turnstile_token":"…"}`; action `email_otp`.
Требуются та же сессия, Origin и CSRF. Ответ содержит `challenge_id`, `expires_in:600`,
`resend_after:60` и сообщение о доставке только после успешной отправки SMTP.
Для существующего и нового email один сценарий, без раскрытия наличия аккаунта.

`POST /v1/web/auth/otp/verify`:
`{"challenge_id":"полученный идентификатор","code":"123456"}`.
Шесть случайных цифр, 10 минут, пять попыток; код привязан к challenge и браузерной
сессии. В БД keyed HMAC, а не plaintext или простой SHA-256 короткого кода.
Неверные попытки фиксируются даже при отказе HTTP. Повторная отправка инвалидирует
старые challenge этой сессии; использованный/исчерпанный код удаляется из записи.
Успех атомарно погашает код и меняет cookie/CSRF. Фронтенду заменить CSRF на новый.
`POST /v1/web/logout` отзывает сессию на сервере и удаляет cookie.

Новый email после guest-демо подтверждает тот же guest Account: расход остаётся.
При входе в существующий email переносится использованное гостевое количество,
а старый guest закрывается. Его деньги/кошелёк/история не объединяются автоматически.
Новый аккаунт без использованного guest-демо получает стандартный разовый пакет.
Платная подписка при входе не меняется. Аккаунты не связываются по IP или совпадению
имени. Привязка email↔Telegram остаётся отдельным будущим подтверждённым действием.

## Ограничения и антиабуз

Начальные значения (панель «Защита демо» и «Демо и модели»):
- Один запрос на новый пакет; 3000 Unicode codepoints ввода, 512 выходных токенов.
- 32 KiB HTTP body на cookie API ДО JSON-разбора, в том числе без Content-Length.
  Сжатые тела не принимаются. Сбор тела ограничен 10 секундами. Этот начальный
  web-периметр ограничивает также подписанный текстовый web route; расширение
  больших платных web-диалогов нужно согласовать отдельно, не снимать guest cap.
- Демо: общий срок 45 секунд и 15 секунд без нового фрагмента; сетевой upstream
  закрывается при отмене. Это не гарантия, что провайдер прекратил начисление.
  Для JSON-клиента демо тоже использует ограниченный upstream stream, не бесконечный thread.
- Не более одной активной демо-генерации на Account и трёх на весь gateway.
- Не более трёх допусков демо с IPv4 или IPv6 /64 за 24 часа; не вечный IP-бан.
- Гостевые сессии: 20/час на сеть, 1000/24ч глобально. HTTP: 120/мин на сеть и
  2000/мин глобально. Turnstile verify: 10/мин на сеть, 300/мин глобально.
- OTP: 5 писем/24ч на email, 20 на сеть, 100 глобально; 60 секунд между отправками.
  Проверка OTP: 20/мин на сеть и 500/мин глобально плюс пять попыток на challenge.
- Общий default из ProductPolicy: 100 демо-попыток/сутки UTC и 30 запросов/мин на аккаунт.

Перед генерацией квота, финансовый резерв, слот, сетевой счётчик и request UUID
проверяются под одной короткой SQL-блокировкой. HTTP/SMTP/Turnstile/model не выполняются
внутри неё. Повтор UUID одной сессии получает 409, не запускает вторую генерацию.
Новый UUID не восстанавливает использованное демо. Отдельные воркеры разделяют
счётчики через SQL; это не process-local словарь. Текущая PostgreSQL-блокировка
глобальная и консервативная; масштабирование требует измерения нагрузки.

Siteverify проверяет success, hostname, action, возраст ≤5 минут. Сохраняется HMAC
использованного токена, а сам токен в БД/метриках не хранится. Тайм-аут/ошибка/
перенаправление/невалидный JSON не разрешают генерацию. Production adapters не
принимают известные демонстрационные секреты Turnstile. Настоящий сервис остаётся
внешней зависимостью; наличие подключённого ключа не доказывает доступность сети.

Адрес клиента берётся из прямого peer. X-Forwarded-For учитывается только от явно
настроенных CIDR proxy и разбирается справа налево. CF-Connecting-IP сам по себе
ничего не доказывает. Uvicorn запускается с `--no-proxy-headers`, чтобы сторонний
middleware не успел довериться заголовку раньше нашей проверки. При другом запуске
сохранить эту настройку, закрыть обход reverse proxy напрямую и протестировать цепь.
Не доверять всему 0.0.0.0/0 или ::/0.

IP нужен в памяти для проверки; в SQL сохраняются domain-separated HMAC сети с
сроком действия окон. Уборка просроченных buckets/OTP/CAPTCHA/request IDs/sessions
выполняется ограниченными пакетами при запросах, старте и раз в минуту при включённом
web. Raw IP, browser fingerprint, Canvas/Audio, evercookie не сохраняются. Ни IP,
ни cookie, ни CAPTCHA не доказывают уникальность человека. Новые IP/почты/очистка
браузера могут обходить отдельные уровни; финансовый предел остаётся независимым.
Нет обещания защиты от всего DDoS: публичный edge нуждается в TLS, ограничении
соединений/размера тела и закрытом origin; приложение не заменяет сетевой firewall.

## Финансовый предохранитель

По умолчанию общий paid demo budget **0 USD**: реальная платная генерация закрыта,
бесплатный `mock:mock-chat` сохраняется. Перед включением внешней модели разработчик
задаёт проверенный максимум стоимости ПОЛНОГО запроса: весь возможный ввод, выход,
reasoning и иные billable units при текущих caps. Таблица DemoModelBound хранит
этот предел и проверенные caps, не выдуманную цену. Без review, положительного
предела и бюджета допуск закрыт. Если изменить caps выше проверенных, он тоже закрыт.

Перед допуском сумма резервируется атомарно. После достоверного usage/cost резерв
заменяется реальной стоимостью. При явном отказе провайдера до генерации возвращается
однократно. Обрыв, тайм-аут и неизвестный расход не возвращают деньги автоматически.
Слот имеет отдельный срок, чтобы сбой процесса не блокировал систему навсегда.
Превышение проверенной стоимости отключает следующие демо до проверки владельцем.
При изменении цен самого провайдера абсолютная гарантия внешнего счёта невозможна:
дополнительно настроить spending cap у поставщика. Отмена не объявляется бесплатной.

## Миграция и данные

20261019_09 не удаляет аккаунты, подписки или usage. Старые DemoGrant получают снимок
выданного лимита (старый default 3); requests_used не обнуляется. Прежние дефолты
3/24000 заменяются на 1/3000 для НОВЫХ выдач; явно отличающиеся настройки сохраняются.
Новые выдачи всегда имеют DemoLimit snapshot: изменение общего числа не пополняет
старые пакеты. Общее выключение выполняется флагом DemoControl.enabled.

## Настройка разработчиком, не владельцем вручную

Окружение `SHLUZ_WEB_*`: ENABLED, SECRET (случайный ≥32 символа), ORIGINS (JSON точных
origins), TRUSTED_PROXIES (JSON CIDR), SECURE_COOKIE; CAPTCHA_SECRET,
CAPTCHA_SITEKEY, CAPTCHA_HOSTNAMES (JSON); SMTP_HOST/PORT/USERNAME/PASSWORD/SENDER/SSL.
Письма всегда через проверенный TLS (STARTTLS или implicit TLS), без debug logging.
Нет provider credentials в браузере. Секреты не публиковать в GitHub или артефактах.
В локальном launcher передавать их через закрытые env установки, не через frontend.

## Ошибки для frontend

`error.code`: web_not_configured, session_required/session_expired, origin_rejected,
csrf_rejected, verification_required/verification_failed/verification_reused,
input_too_large/body_too_large, model_selection_unavailable/model_not_allowed,
demo_exhausted/demo_busy/demo_temporarily_unavailable, too_many_requests,
request_already_used, mail_not_configured/mail_unavailable, invalid_or_expired_code,
invalid_request. В части моделей сохраняются OpenAI-style ошибки общего gateway.
Показывать понятный текст по code; не логировать payload/OTP/cookies в analytics.
OTP verification после успешной смены cookie требует нового CSRF во всех вкладках.

Граница готовности: автоматические тесты проверяют код и синтетические внешние
ответы, а не живую доставку SMTP, реальную проверку Turnstile, настоящие платежи или
качество ещё не подключённой модели. После настройки инфраструктуры нужен живой
приёмочный прогон с одним ограниченным реальным запросом.

### Данные внешних сервисов

Наши таблицы защиты не содержат сырого IP или устойчивого отпечатка. При проверке
Turnstile IP отправляется Cloudflare; её виджет обрабатывает собственные сигналы
согласно политике этого сервиса. SMTP-поставщик получает адрес и письмо с кодом.
Не обещать отсутствие любых третьих сторон или анонимность email-аккаунта.
Основные сетевые/почтовые/финансовые лимиты изменяются в «Защите демо».
Жёсткие защитные границы протокола (32 КиБ, срок OTP 10 минут, 5 попыток,
60 секунд между письмами) не являются тарифными настройками.
