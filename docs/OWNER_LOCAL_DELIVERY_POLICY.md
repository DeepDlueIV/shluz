# NoClip / SHLUZ: неизменный стандарт локальной приёмки и обновлений

> Зафиксировано по требованию владельца 24.10.2026. **Это обязательный UX-критерий поставки**,
> а не утверждение о том, что описанный обновляющий механизм уже реализован.
> Архитектурная унификация и разработка Control Center — предложения к реализации
> после безопасной проверки работающей системы. Не изменять продакшен и базы по этому документу.

## 1. Что владелец считает готовой локальной сборкой

Владелец получает точную ссылку на **проверенную и закреплённую версию**.
Максимум действий при обновлении: скачать ZIP, распаковать **куда угодно**, открыть
**один явно названный файл**. Всё остальное — обнаружение прежней установки,
проверка зависимостей, проверка целостности, backup, обновление кода/образов,
переключение, запуск, статус и диагностика — выполняется программой.
Вторичная цель: полностью убрать необходимость скачивать ZIP, добавив
кнопку «Проверить и установить обновление» в уже существующую локальную админку.

**Запрещено делать стандартным сценарием** ручное копирование .env, перенос базы
между ZIP, выбор Git-ветки, Docker-команды, правку портов, выбор второго
параллельного шлюза, переименование папок или ввод прежних ключей заново.
Исключения: самый первый ввод секретов/авторизация внешнего сервиса,
явная миграция с несовместимой схемой, разрешение на существенные действия.
При исключении заранее дать ровно одну короткую причину и необходимые действия.

## 2. Одна установка, две независимые сущности: программа и данные

- Каноническая локальная установка **`D:\NoClip\Shluz`**. Нельзя создавать
  рядом вторые самостоятельные `NoClip-SHLUZ-Portable-*` и выдавать их за рабочую.
- **Программа:** неизменяемые проверенные версии под `versions/<id>` или в Docker
  с закреплёнными digests. Активный указатель на принятую версию.
- **Долговечные данные:** существующие Docker named volumes (история, кошельки,
  ключи коннектора), пользовательская конфигурация, защищённые секреты и backups.
  Их жизненный цикл не связан с распакованным ZIP и не меняется при обновлении кода.
- Не требовать переноса AppData при каждой новой версии. Работающая
  конфигурация `D:\NoClip\Shluz\config` и нынешние Docker volumes — исходная
  точка для обновлений; изменение расположения только после проверки и согласования.
- Слово «portable» относится к **поставке лаунчера**, а не к Docker-базам:
  перенос ZIP на другой компьютер не переносит пользователей или Docker Desktop.
  Не обещать настоящую полностью переносимую установку.

## 3. Требуемое поведение единственной кнопки

1. Из любого каталога распаковки однокликовый bootstrap находит каноническую
   установку и ранее сохранённые volumes/config; не создаёт новую БД поверх
   существующей и не запускает второй Telegram polling.
2. Проверяет подписанный/закреплённый trusted release manifest, SHA256 и digests
   образов, совместимость схем и доступное место. Только mock в CI; секреты не в логах.
3. Создаёт согласованный backup **перед** изменением/миграцией, проверяет
   целостность SQLite (включая WAL) и наличие файлов восстановления.
4. Распаковывает/загружает в staging, проводит preflight, останавливает только
   принадлежащие NoClip процессы, переключает активную версию и проверяет health.
5. При успехе один раз открывает **существующую** локальную админку
   `http://127.0.0.1:18000/admin`, показывает текущую версию и статусы:
   основной Gateway, Telegram/Mini App, web bridge и туннели.
6. При сбое возвращает прежние процессы/бинарную версию где это безопасно;
   **никогда автоматически не откатывает БД поверх новых записей**.
   Сообщает одну понятную причину и кнопку «Вернуть предыдущую версию»
   только после проверки совместимости данных.
7. Старые контейнеры и volumes не удаляются автоматически. Не использовать
   `docker compose down -v`, `docker volume prune` или `docker system prune`.

Нужно тестировать повторный запуск без изменений (идемпотентность), обновление
после перезагрузки, конфликт PID/port, недоступный Docker/VPN/tunnel, повреждённый
state, отказ середины миграции, запас места, остановку и настоящую сохранность данных.
Версия готова к передаче владельцу только после CI и самостоятельной воспроизводимой
приёмки доступных сценариев. Отдельно указать, что из Windows ещё не проверено.

## 4. Одна админка на вид, разные полномочия внутри

**Не создавать вторую отдельную панель для владельца.** Развивать нынешнюю
`http://127.0.0.1:18000/admin`: сохранить пользователей, тарифы, кошельки,
модели, расходы, диагностику, Telegram. Дополнить разделами:
«Система», «Провайдеры/ключи», «Подключения/туннели», «Резервные копии»,
«Версия/обновление» — без дублирования бизнес-логики.

Для host-операций (Docker, ngrok/cloudflared, backup, секреты Windows)
использовать **отдельный минимально привилегированный локальный управляющий
процесс**, а не давать публичному Gateway доступ к Docker socket, файловой системе
хоста или произвольному shell. Он обслуживает только локальный loopback/защищённый
IPC и фиксированные allowlisted операции, с отдельной авторизацией, CSRF и аудитом.
Одну UI-поверхность можно собрать через локальный proxy/UI-слой, оставляя закрытым
доступ к управляющему процессу из публичных туннелей.

Provider keys вводятся владельцем один раз через защищённую форму, хранятся
в надлежащем секретном хранилище ОС (для Windows возможен DPAPI с правильной
привязкой к учётной записи), и подставляются только в необходимые server-side
сервисы. Telegram/Desktop/браузер не получают прямой Venice API Key.
Для перезапуска контейнеров после замены ключа нужен controlled recreate
с сохранением volume, а не один `docker restart` старого окружения.

## 5. Исходный код, main, выпуск и развёртывание

- Рабочие feature-ветки — нормальны. **`main` не должен содержать незавершённый
  код** и не обязан быть мгновенным зеркалом всех рабочих веток.
- `main` — стабильная, цельная интеграционная версия после тестов и согласованной
  приёмки. Не merge только ради косметического соответствия Production.
- Для каждого компонента отслеживать точный **commit SHA + образ/release +
  результат CI + статус локальной/live приёмки**. Не считать git-merge равным
  локальной установке, и не путать релиз backend со сборкой сайта на Vercel.
- **Vercel обслуживает только NoClip Web**. Развёртывание сайта из закреплённой
  рабочей ветки допускается по разрешению владельца и не требует немедленного merge
  в `main`. Нельзя позволять следующему авто-деплою из устаревшего `main`
  случайно заменить уже принятую Production-версию; настройку gating/branch
  владелец утверждает совместно с ответственным агентом сайта.
- Backend/Gateway/Telegram/launcher выпускаются отдельной версией; Docker и
  пользовательская база остаются локальными до отдельного решения о сервере.
- Сайт разрабатывается отдельным агентом: не менять его код/production или
  ветку без координации. Менять API-контракт только с совместимыми тестами.

## 6. Будущее размещение на сервере

Выделить переносимую бизнес-логику SHLUZ и контракт локального control-plane.
Для Windows используется локальный supervisor; для Linux/VPS — соответствующий
системный сервис и защищённое хранилище секретов. GUI остаётся логически одним,
но server control endpoint не становится публичным API. Управление на VPS только
через защищённый административный канал/права, не через общедоступный `/v1/*`.
Реальная миграция Docker volumes, SQLite/бэкапов и секретов потребует отдельной
проверки совместимости, backup/restore и разрешения; она не выполняется сейчас.

## 7. Обязательная инструкция к КАЖДОМУ локальному выпуску

Сообщать владельцу компактно и **однозначно**:

1. **Версия и ссылка:** точный архив/релиз/SHA, какие проверки прошли.
2. **Куда:** канонический путь неизменен; архив можно распаковать в Downloads.
3. **Что нажать:** имя ОДНОГО запускающего файла из архива.
4. **Что будет со старой версией:** автоматически сохранена / не тронута /
   требуется разовое действие по явно указанной причине.
5. **Что проверить:** один-два реальных пользовательских сценария.
6. **Как остановить:** одна явно названная кнопка/ярлык, а не Docker CLI.

**Приёмочный критерий Product Owner:** скачать → распаковать → один запуск
→ актуальная система работает, данные и ключи сохранены, версия видна в админке.
Любое большее число ручных действий — дефект процесса поставки,
который нужно исправлять, а не перекладывать на владельца.
