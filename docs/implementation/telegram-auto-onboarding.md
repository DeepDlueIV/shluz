# Автоматическое подключение Telegram

Цель владельца: пользователь нажимает Start; создание/привязка аккаунта и внутреннего
доступа выполняются приложением. Владелец оценивает UI, а не выпускает ключи и правит JSON.
Режим закрытой беты сохраняется: приглашение с выбранным тарифом подключает сразу;
обычный Start создаёт заявку, разрешение которой — бизнес-решение в админке.
Нет автоматического публичного доступа к платным моделям.

## Реализация
- Gateway хранит заявки/разрешения и одноразовые приглашения. Привязка только по
  числовому Telegram ID от доверенного сервера бота; не по username/имени.
- Служебный секрет с узкой областью действия создаётся шлюзом атомарно в Docker-томе,
  монтируется боту только для чтения. Это не admin/bootstrap/provider key.
- Бот получает краткоживущую подписанную сессию на конкретный доступ, использует обычные
  /v1 endpoints. На каждом запросе gateway проверяет актуальный статус аккаунта/доступа.
- Старый закрытый список читается опционально для миграции: действительный персональный
  ключ проверяется шлюзом, прежние аккаунт/тариф/расход/история сохраняются. Отозванный
  ключ не восстанавливается и не позволяет получить новое разрешение.
- Одноразовые приглашения (24 часа) и одобрения не сбрасывают квоты/подписки; блокировка
  запрещает вход, даже с новым приглашением. Повторная активация только администратором.
- Локальные правки и секреты Codex не доступны здесь. Публикуются изменения кода в
  текущую feature-ветку, main и компьютер владельца не меняются.

## Проверки
Тесты прежде кода: аутентификация служебного канала, pending без платного доступа,
приглашение/одобрение/повтор/гонки, лимиты, блокировка/истечение сессии, подмена ID,
миграция и отзыв старого ключа, UI CSRF, отсутствие секретов, новый Start через dispatcher.
Выполнить весь pytest, lint, миграцию на отдельной SQLite и CI Docker/Chromium.
