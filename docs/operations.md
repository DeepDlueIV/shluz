# Эксплуатация Shluz простыми словами

Этот документ объясняет, что нужно знать владельцу сервиса без глубоких знаний системного администрирования.

## Где находятся настройки

Все закрытые настройки передаются серверу через файл `.env` либо через раздел Secrets у выбранного хостинга.

| Переменная | Для чего нужна |
|---|---|
| `SHLUZ_ENVIRONMENT` | Название среды: `development`, `staging` или `production` |
| `SHLUZ_BOOTSTRAP_API_TOKEN` | Временный ключ доступа к API Shluz |
| `SHLUZ_ADMIN_USERNAME` | Логин владельца для `/admin` |
| `SHLUZ_ADMIN_PASSWORD` | Пароль владельца для `/admin` |
| `SHLUZ_ACTIVE_PROVIDER` | Активный провайдер: `mock` для теста или `venice` для реальной модели |
| `SHLUZ_VENICE_API_KEY` | Секретный API-ключ Venice |
| `SHLUZ_VENICE_BASE_URL` | Адрес Venice API; обычно менять не нужно |
| `SHLUZ_VENICE_TIMEOUT_SECONDS` | Максимальное ожидание ответа Venice |
| `SHLUZ_VENICE_ANALYTICS_LOOKBACK` | Период аналитики в панели, например `7d` |

Полные значения ключей не передаются в HTML и не должны попадать в журналы.

## Два уровня учёта

### Данные поставщика

Уровень Venice уже поддерживается. Он показывает:

- общий баланс аккаунта;
- можно ли сейчас расходовать средства;
- срок действия и тариф API-ключа, если Venice их сообщает;
- доступные модели и их цены;
- ограничения запросов и токенов;
- доступную аналитику общего расхода.

Эти данные относятся ко всему серверному ключу Venice, а не к отдельным пользователям Shluz.

### Данные пользователей

Появятся после подключения PostgreSQL/Supabase:

- аккаунты и способы входа;
- роли и права;
- тариф и подписка;
- квота и остаток;
- токены и себестоимость каждого запроса;
- ваша цена и маржа;
- блокировки, возвраты и журнал административных действий.

Разделение важно: Venice знает расход общего ключа, а Shluz должен самостоятельно знать, какой пользователь создал этот расход.

## Быстрая проверка без расходов

Оставьте в `.env`:

```dotenv
SHLUZ_ACTIVE_PROVIDER=mock
```

Запустите:

```bash
docker compose up --build
```

Откройте:

- <http://localhost:8000/admin> — главная панель;
- <http://localhost:8000/admin/providers/venice> — страница провайдера;
- <http://localhost:8000/docs> — наглядное выполнение API-запросов;
- <http://localhost:8000/health> — состояние сервера.

Режим `mock` не отправляет запросы во внешние сервисы и не тратит деньги.

## Подключение Venice

1. Создайте отдельный тестовый API-ключ Venice с ограниченным балансом или лимитом.
2. Не отправляйте его в чат и не добавляйте в GitHub.
3. Сохраните в `.env` либо в Secrets хостинга:

```dotenv
SHLUZ_ACTIVE_PROVIDER=venice
SHLUZ_VENICE_API_KEY=ваш_ключ
```

4. Перезапустите сервис:

```bash
docker compose up -d --build
```

5. Откройте `/admin/providers/venice` и убедитесь, что отображаются подключение, баланс, модели и лимиты.
6. Откройте `/docs`, авторизуйтесь токеном Shluz и выполните один небольшой тестовый запрос.

Платный запрос к Venice автоматически не повторяется: это защищает от двойного списания при неясном сетевом сбое.

## Что означают типичные ошибки

| Ситуация | Что увидит клиент | Что проверить владельцу |
|---|---|---|
| Неверный или просроченный ключ | Ошибка учётных данных провайдера | `SHLUZ_VENICE_API_KEY` и срок ключа |
| Недостаточный баланс | Баланс провайдера недоступен | Баланс Venice и валюту списания |
| Превышен лимит | Достигнут лимит провайдера | RPM/TPM на странице Venice |
| Venice временно недоступен | Временная ошибка провайдера | `/admin/providers/venice`, статус Venice и журналы сервера |
| Аналитика не загрузилась | Остальные данные продолжают работать | Повторить позже; аналитика Venice считается необязательной |

Технические подробности ответа Venice не показываются пользователю, чтобы не раскрывать внутреннюю конфигурацию.

## Что нельзя делать

- Не отправлять файл `.env` другим людям.
- Не загружать `.env` в GitHub.
- Не записывать реальные ключи прямо в исходный код.
- Не использовать одинаковые секреты для тестового и рабочего сервера.
- Не публиковать сервер напрямую в интернет без HTTPS.
- Не давать Harness прямой ключ Venice: Harness должен знать только адрес Shluz и пользовательский токен Shluz.

## Развёртывание на новом сервере

Минимальный порядок:

1. Установить Docker и Docker Compose.
2. Скачать репозиторий или готовый Docker-образ.
3. Создать `.env` из `.env.example`.
4. Установить уникальные длинные токен и пароль.
5. Добавить ключ провайдера через серверные Secrets.
6. Запустить `docker compose up -d --build`.
7. Проверить `/health`, `/admin`, `/admin/providers/venice` и `/docs`.
8. Настроить домен и HTTPS через облачную платформу или reverse proxy.
9. Ограничить доступ к административной панели на уровне сети, если хостинг это позволяет.

## Как понять, что сервер работает

Адрес `/health` должен вернуть примерно такой ответ:

```json
{
  "status": "ok",
  "service": "shluz",
  "version": "0.1.0"
}
```

Если он не открывается, сначала проверьте журнал контейнера:

```bash
docker compose logs --tail=100 shluz
```

## Ротация секретов

Ротация означает замену старого ключа новым.

1. Создать новый ключ.
2. Заменить значение в хранилище Secrets или `.env`.
3. Перезапустить сервис: `docker compose up -d`.
4. Проверить `/health`, `/admin/providers/venice` и один тестовый запрос.
5. Отозвать старый ключ у поставщика.
6. Удалить старый секрет из менеджера паролей и тестовых файлов.

После появления пользовательских токенов Shluz будет поддерживать их независимую ротацию без одновременного отключения всех клиентов.

## Резервные копии

Постоянной пользовательской базы данных пока нет, поэтому резервировать пользовательские данные ещё нечего.

После подключения PostgreSQL/Supabase необходимо:

- включить ежедневные автоматические резервные копии;
- хранить хотя бы одну копию отдельно от основного сервера;
- раз в месяц проверять восстановление на тестовой среде;
- определить срок хранения истории запросов и расходов.

## Перед публичным запуском

До выдачи доступа реальным пользователям обязательны:

- HTTPS;
- полноценная регистрация и пользовательские токены;
- лимиты запросов и расходов;
- база данных;
- аудит административных действий;
- защита от перебора паролей;
- мониторинг ошибок и доступности;
- юридическая проверка условий коммерческого использования поставщиков моделей;
- политика хранения и удаления пользовательских данных.
