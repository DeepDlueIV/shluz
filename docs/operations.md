# Эксплуатация Shluz простыми словами

Этот документ предназначен для владельца сервиса без глубоких знаний системного администрирования.

## Закрытые настройки

Секреты передаются через локальный `.env` либо раздел **Secrets** выбранного хостинга.

| Переменная | Для чего нужна |
|---|---|
| `SHLUZ_ENVIRONMENT` | Среда: `development`, `staging` или `production` |
| `SHLUZ_BOOTSTRAP_API_TOKEN` | Технический токен для первоначальной настройки и локальной проверки |
| `SHLUZ_ADMIN_USERNAME` | Логин владельца для `/admin` |
| `SHLUZ_ADMIN_PASSWORD` | Пароль владельца для `/admin` |
| `SHLUZ_DATABASE_URL` | Строка подключения к SQLite или PostgreSQL/Supabase |
| `SHLUZ_CREDIT_UNIT_USD` | Денежный эквивалент одного внутреннего кредита |
| `SHLUZ_RESERVATION_TTL_SECONDS` | Срок временной резервации запроса |
| `SHLUZ_ACTIVE_PROVIDER` | `mock` для бесплатного теста или `venice` для живой модели |
| `SHLUZ_VENICE_API_KEY` | Секретный API-ключ Venice |
| `SHLUZ_VENICE_BASE_URL` | Адрес Venice API; обычно менять не нужно |
| `SHLUZ_VENICE_TIMEOUT_SECONDS` | Максимальное ожидание Venice |
| `SHLUZ_VENICE_ANALYTICS_LOOKBACK` | Период аналитики Venice, например `7d` |

Пароли, токены, ключи и строка базы не должны попадать в HTML, логи или GitHub.

## Быстрая проверка без расходов

Оставьте в `.env`:

```dotenv
SHLUZ_ACTIVE_PROVIDER=mock
SHLUZ_DATABASE_URL=sqlite+pysqlite:///./data/shluz.db
SHLUZ_CREDIT_UNIT_USD=0.001
SHLUZ_RESERVATION_TTL_SECONDS=900
```

Запустите:

```bash
docker compose up --build
```

Откройте:

- <http://localhost:8000/admin> — сводка;
- <http://localhost:8000/admin/users> — пользователи, тарифы, остатки и токены;
- <http://localhost:8000/admin/plans> — создание и изменение тарифов;
- <http://localhost:8000/admin/usage> — себестоимость, выручка и маржа;
- <http://localhost:8000/admin/providers/venice> — Venice;
- <http://localhost:8000/docs> — ручная проверка API;
- <http://localhost:8000/health> — состояние сервера.

Режим `mock` не обращается к внешним моделям и не расходует деньги.

## База данных

### Локальная SQLite

Docker хранит файл в постоянном томе `shluz_data`. Обычная остановка не удаляет данные:

```bash
docker compose down
```

Команда ниже удаляет контейнеры **и локальную базу**:

```bash
docker compose down -v
```

Используйте её только когда данные действительно больше не нужны.

### PostgreSQL или Supabase

Для удалённой базы код менять не нужно. В Secrets сервера задаётся:

```dotenv
SHLUZ_DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:5432/postgres?sslmode=require
```

Контейнер при старте применяет миграции Alembic. Строка подключения не должна храниться в репозитории.

В Supabase прикладные таблицы Shluz должны быть закрыты от ролей `anon` и `authenticated`; приложение подключается к PostgreSQL только с сервера.

## Пользователи и доступы

Раздел `/admin/users` позволяет:

- создать аккаунт;
- увидеть роль, статус и способы входа;
- назначить или снять тариф;
- увидеть месячные лимиты и остатки;
- выдать токен для Harness, сайта, Telegram или другого API;
- увидеть только безопасный префикс токена;
- отозвать токен;
- видеть себестоимость, расчётную выручку и маржу пользователя.

Полный токен показывается один раз. В базе хранится только SHA-256-хэш, короткий префикс, назначение, канал и служебные даты. Потерянный токен нужно отозвать и создать заново.

Административные формы защищены CSRF-токеном, а страница с новым секретом запрещена кэшированию браузером.

## Тарифы

Раздел `/admin/plans` позволяет создать и изменить:

- код и название;
- активность;
- справочную месячную цену;
- лимит запросов;
- лимит внутренних кредитов;
- лимит себестоимости поставщиков;
- резерв кредитов на один запрос;
- процент наценки.

Пустой или нулевой лимит означает отсутствие соответствующего ограничения.

Отключённый тариф прекращает доступ пользователей, которым он назначен. Удалять тариф с историей не нужно: безопаснее отключить его, чтобы старые записи расходов сохранили связь.

## Как применяются ограничения

Расчётный период — календарный месяц по UTC.

Перед обращением к модели Shluz:

1. Проверяет аккаунт и персональный токен.
2. Проверяет активную подписку и тариф.
3. Проверяет лимит запросов.
4. Проверяет внутренние кредиты.
5. Проверяет лимит себестоимости.
6. Создаёт временную резервацию запроса и кредитов.

После ответа резервация заменяется точными токенами и стоимостью. При известной ошибке поставщика резерв освобождается, а ошибка остаётся в журнале. Зависшая резервация перестаёт учитывать лимит после `SHLUZ_RESERVATION_TTL_SECONDS`.

Текущая первая версия использует фиксированный резерв тарифа. Фактическая стоимость отдельного ответа иногда может оказаться выше резерва; в этом случае точный расход записывается, а следующие запросы блокируются. Позднее можно добавить предварительную оценку по конкретной модели и максимальной длине ответа.

## Внутренние кредиты, выручка и маржа

```text
расчётная выручка = себестоимость × (1 + наценка / 100)
кредиты = округление вверх(выручка / цена кредита)
маржа = выручка − себестоимость
```

По умолчанию:

```dotenv
SHLUZ_CREDIT_UNIT_USD=0.001
```

Пример: себестоимость запроса `0.008 USD`, наценка `25%`:

```text
выручка = 0.010 USD
кредиты = 10
маржа = 0.002 USD
```

Это расчётная экономика, а не подтверждение банковского платежа. Фактические платежи, возвраты и задолженности будут отдельными таблицами после подключения платёжной системы.

## Публичные ошибки лимитов

Клиент получает стандартную структуру ошибки без внутренних секретов:

| Код | Значение |
|---|---|
| `subscription_required` | Нет активного тарифа |
| `request_limit_exceeded` | Исчерпан лимит запросов |
| `credit_limit_exceeded` | Исчерпаны внутренние кредиты |
| `spend_limit_exceeded` | Исчерпан лимит себестоимости |

## Как выдать доступ

1. Создайте тариф в `/admin/plans`.
2. Создайте аккаунт в `/admin/users`.
3. Назначьте тариф.
4. Нажмите **Выдать доступ**.
5. Выберите канал и понятное название токена.
6. Скопируйте `shluz_...`, пока он виден.
7. Передайте его безопасным способом.

Клиент отправляет:

```text
Authorization: Bearer shluz_...
```

Для разных устройств и каналов создавайте отдельные токены: их можно отзывать независимо, а расход виден точнее.

## Если токен скомпрометирован

1. Откройте `/admin/users`.
2. Найдите токен по названию и префиксу.
3. Нажмите **Отозвать**.
4. Создайте новый токен.
5. Обновите его только на нужном устройстве.

Отзыв применяется со следующего запроса.

## Подключение Venice

Без реального ключа живые запросы Venice не выполняются. Для подключения:

1. Создайте отдельный тестовый ключ Venice с небольшим лимитом.
2. Не отправляйте ключ в чат и не добавляйте его в GitHub.
3. Сохраните в `.env` или Secrets:

```dotenv
SHLUZ_ACTIVE_PROVIDER=venice
SHLUZ_VENICE_API_KEY=ваш_ключ
```

4. Перезапустите:

```bash
docker compose up -d --build
```

5. Проверьте `/admin/providers/venice`.
6. Выполните один небольшой запрос через `/docs`.

Платный POST-запрос автоматически не повторяется, чтобы не создать двойное списание при неясном сетевом сбое.

## Автоматическая проверка Docker

GitHub Actions выполняет:

1. Проверку кода Ruff.
2. Применение миграций к чистой SQLite-базе.
3. Все тесты pytest.
4. Сборку Docker-образа.
5. Запуск контейнера в режиме `mock`.
6. Ожидание статуса `healthy`.
7. Проверку `/health`.
8. Один тестовый запрос к `mock-chat`.
9. Вывод логов при ошибке и удаление контейнера.

Это проверяет не только возможность собрать образ, но и реальный запуск приложения внутри него.

## Резервные копии

Для SQLite резервируется Docker-том или файл базы после остановки сервиса.

Для PostgreSQL/Supabase:

- включите автоматические резервные копии;
- храните хотя бы одну копию отдельно;
- периодически проверяйте восстановление;
- определите срок хранения истории расхода.

## Перенос на другой сервер

1. Установить Docker и Docker Compose.
2. Скачать репозиторий или образ.
3. Создать `.env` из `.env.example`.
4. Установить уникальные длинные секреты.
5. Указать строку базы и ключ поставщика через Secrets.
6. Запустить `docker compose up -d --build`.
7. Проверить `/health`, `/admin` и `/docs`.
8. Настроить домен и HTTPS.
9. Ограничить `/admin` на уровне сети.

## Перед публичным запуском

Нужны:

- HTTPS;
- самостоятельная регистрация и восстановление доступа;
- подтверждение email или привязка Telegram;
- реальная платёжная система;
- аудит административных действий;
- защита от перебора паролей;
- мониторинг ошибок и доступности;
- юридическая проверка коммерческого использования поставщиков;
- политика хранения и удаления пользовательских данных.
