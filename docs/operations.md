# Эксплуатация Shluz простыми словами

Этот документ объясняет, что нужно знать владельцу сервиса без глубоких знаний системного администрирования.

## Где находятся настройки

Все закрытые настройки передаются серверу через файл `.env` либо через раздел Secrets у выбранного хостинга.

| Переменная | Для чего нужна |
|---|---|
| `SHLUZ_ENVIRONMENT` | Название окружения: `development`, `staging` или `production` |
| `SHLUZ_BOOTSTRAP_API_TOKEN` | Временный ключ доступа к API Shluz |
| `SHLUZ_ADMIN_USERNAME` | Логин владельца для `/admin` |
| `SHLUZ_ADMIN_PASSWORD` | Пароль владельца для `/admin` |

Значения ключей поставщиков будут добавляться позднее. Они также должны находиться только в серверных Secrets.

## Что нельзя делать

- Не отправлять файл `.env` другим людям.
- Не загружать `.env` в GitHub.
- Не записывать реальные ключи прямо в исходный код.
- Не использовать одинаковые секреты для тестового и рабочего сервера.
- Не публиковать сервер напрямую в интернет без HTTPS.

## Развёртывание на новом сервере

Минимальный порядок:

1. Установить Docker и Docker Compose.
2. Скачать репозиторий или готовый Docker-образ.
3. Создать `.env` из `.env.example`.
4. Установить уникальные длинные токен и пароль.
5. Запустить `docker compose up -d --build`.
6. Проверить `/health`, `/admin` и `/docs`.
7. Настроить домен и HTTPS через облачную платформу или reverse proxy.
8. Ограничить доступ к административной панели, если хостинг позволяет это сделать на уровне сети.

## Как понять, что сервер работает

Адрес `/health` должен вернуть примерно такой ответ:

```json
{
  "status": "ok",
  "service": "shluz",
  "version": "0.1.0"
}
```

Если он не открывается, сначала проверьте журнал контейнера:

```bash
docker compose logs --tail=100 shluz
```

## Ротация секретов

Ротация означает замену старого ключа новым.

1. Создать новый длинный случайный секрет.
2. Заменить значение в хранилище Secrets или `.env`.
3. Перезапустить сервис: `docker compose up -d`.
4. Проверить `/health` и вход в `/admin`.
5. Удалить старый секрет из менеджера паролей и всех тестовых файлов.

После появления пользовательских токенов Shluz будет поддерживать более мягкую ротацию без одновременного отключения всех клиентов.

## Резервные копии

В первом этапе постоянной базы данных ещё нет, поэтому резервировать пользовательские данные пока нечего.

После подключения PostgreSQL/Supabase необходимо:

- включить ежедневные автоматические резервные копии;
- хранить хотя бы одну копию отдельно от основного сервера;
- раз в месяц проверять восстановление на тестовом окружении;
- определить срок хранения истории запросов и расходов.

## Перед публичным запуском

До выдачи доступа реальным пользователям обязательны:

- HTTPS;
- полноценная регистрация и пользовательские токены;
- лимиты запросов и расходов;
- база данных;
- аудит административных действий;
- защита от перебора паролей;
- контролируемые таймауты внешних провайдеров;
- мониторинг ошибок и доступности;
- юридическая проверка условий использования поставщиков моделей.
