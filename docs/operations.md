# Эксплуатация Shluz простыми словами

Этот документ объясняет владельцу сервиса, где находятся данные, как смотреть расходы и что нельзя делать с секретами.

## Где находятся настройки

Закрытые настройки передаются через локальный `.env` либо раздел Secrets выбранного хостинга.

| Переменная | Для чего нужна |
|---|---|
| `SHLUZ_ENVIRONMENT` | Среда: `development`, `staging` или `production` |
| `SHLUZ_BOOTSTRAP_API_TOKEN` | Временный ключ доступа к публичному API Shluz |
| `SHLUZ_ADMIN_USERNAME` | Логин владельца для `/admin` |
| `SHLUZ_ADMIN_PASSWORD` | Пароль владельца для `/admin` |
| `SHLUZ_DATABASE_URL` | SQLite локально либо PostgreSQL/Supabase на сервере |
| `SHLUZ_DATABASE_ECHO` | Технический вывод SQL; в рабочей среде оставлять `false` |
| `SHLUZ_ACTIVE_PROVIDER` | `mock` для бесплатного теста или `venice` для живых запросов |
| `SHLUZ_VENICE_API_KEY` | Секретный ключ Venice |
| `SHLUZ_VENICE_BASE_URL` | Адрес Venice API; обычно менять не нужно |
| `SHLUZ_VENICE_TIMEOUT_SECONDS` | Максимальное ожидание ответа Venice |
| `SHLUZ_VENICE_ANALYTICS_LOOKBACK` | Период внешней аналитики Venice, например `7d` |

Строка подключения к базе содержит пароль и считается таким же секретом, как API-ключ.

## Что видно в браузере

После запуска откройте `/admin`.

- `/admin/users` — пользователь, роль, статус, способы входа, тариф, внутренний баланс и себестоимость его запросов;
- `/admin/plans` — цена, включённые кредиты, права, ограничения и число подписок;
- `/admin/usage` — канал, модель, токены, себестоимость, внутреннее списание и ошибки;
- `/admin/tokens` — название клиентского ключа, безопасный префикс, права и срок действия;
- `/admin/providers/venice` — общий баланс, модели, цены и ограничения поставщика.

Полные секреты и хэши токенов в HTML не передаются.

## Два уровня финансового контроля

### Поставщик

Venice сообщает общий баланс и расход серверного ключа. Это закупочная сторона сервиса.

### Пользователи Shluz

Shluz самостоятельно записывает, кто создал запрос, через какой канал, сколько было токенов и какова себестоимость. Позднее к этой записи добавятся ваша розничная цена и маржа.

Запись расхода создаётся **до** обращения к платному провайдеру. Если база недоступна, платный вызов блокируется, чтобы расход не прошёл незамеченным.

## Локальная база SQLite

Значение по умолчанию:

```dotenv
SHLUZ_DATABASE_URL=sqlite+pysqlite:///./data/shluz.db
```

При запуске через Docker файл хранится в постоянном томе `shluz_data`. Обычный перезапуск контейнера данные не удаляет.

Для резервной копии локальной проверки остановите контейнер и скопируйте файл базы из тома либо используйте экспорт Docker volume. Не выполняйте копирование работающего SQLite-файла без проверки целостности.

## PostgreSQL и Supabase

Для рабочего сервера рекомендуется PostgreSQL/Supabase:

```dotenv
SHLUZ_DATABASE_URL=postgresql+psycopg://USER:PASSWORD@HOST:6543/postgres?sslmode=require
```

Порядок подключения Supabase:

1. Создать или восстановить активный проект.
2. Взять строку подключения из раздела Database.
3. Применить `supabase/migrations/20260929_01_accounting_foundation.sql`.
4. Сохранить строку подключения только в Secrets сервера.
5. Запустить Shluz и проверить `/admin`, `/health` и тестовый запрос.
6. Включить резервные копии и проверить восстановление на отдельной среде.

Миграция включает Row Level Security и не создаёт публичных политик. На первом этапе таблицы доступны только серверной роли. Не применяйте миграцию к проекту, который вы не выбрали как рабочий.

## Быстрая проверка без расходов

Оставьте:

```dotenv
SHLUZ_ACTIVE_PROVIDER=mock
```

Запустите:

```bash
docker compose up --build
```

Откройте `/docs`, авторизуйтесь значением `SHLUZ_BOOTSTRAP_API_TOKEN` и вызовите модель `mock-chat`. Запрос появится в `/admin/usage`, но его стоимость будет нулевой.

## Живое подключение Venice

Адаптер Venice можно проверить тестами без ключа, но реальные ответы, баланс и каталог аккаунта доступны только после ввода ключа:

```dotenv
SHLUZ_ACTIVE_PROVIDER=venice
SHLUZ_VENICE_API_KEY=ваш_ключ
```

После изменения настроек перезапустите сервис и сначала выполните один короткий запрос. Платный POST-запрос автоматически не повторяется, чтобы не вызвать двойное списание при неясном сетевом сбое.

## Типичные ошибки

| Ситуация | Поведение Shluz | Действие владельца |
|---|---|---|
| База недоступна до запроса | Провайдер не вызывается | Проверить `SHLUZ_DATABASE_URL`, доступность PostgreSQL и диск |
| Неверный ключ Venice | Безопасная ошибка учётных данных | Проверить ключ и срок действия |
| Недостаточный баланс | Запрос отклонён | Пополнить баланс или сменить провайдера |
| Превышен RPM/TPM | Возвращается ошибка лимита | Проверить страницу Venice и настроить очередь/другой тариф |
| Ответ получен, но финальная запись не сохранилась | Ответ не запрашивается повторно; ошибка попадает в журнал | Восстановить базу и проверить событие `pending` |

## Что нельзя делать

- отправлять `.env`, строку базы или ключ Venice в чат;
- загружать `.env` в GitHub;
- встраивать ключ поставщика в Harness, сайт или Telegram;
- хранить сырой пользовательский токен в базе;
- включать `SHLUZ_DATABASE_ECHO=true` в production без необходимости;
- публиковать сервер без HTTPS;
- удалять Docker volume или базу без резервной копии.

## Развёртывание на новом сервере

1. Установить Docker и Docker Compose.
2. Скачать репозиторий или готовый образ.
3. Создать `.env` из `.env.example`.
4. Установить уникальные токен и пароль администратора.
5. Выбрать SQLite для теста либо PostgreSQL/Supabase для рабочей среды.
6. Добавить ключ провайдера через Secrets.
7. Запустить `docker compose up -d --build`.
8. Проверить `/health`, `/admin`, `/docs` и один тестовый запрос.
9. Настроить домен, HTTPS, резервные копии и мониторинг.

## Ротация секретов

1. Создать новый секрет у соответствующего поставщика.
2. Заменить его в Secrets или `.env`.
3. Перезапустить сервис.
4. Проверить состояние и один короткий запрос.
5. Отозвать старый секрет.

Пользовательские токены будут выпускаться отдельно для каждого канала, поэтому их можно будет отзывать без остановки остальных клиентов.

## Перед публичным запуском

Обязательны:

- HTTPS;
- PostgreSQL/Supabase и автоматические резервные копии;
- регистрация, подтверждение личности и персональные токены;
- применение тарифов, квот и блокировки перерасхода;
- платёжная интеграция и аудит административных действий;
- защита от перебора пароля администратора;
- мониторинг ошибок, очередей и доступности провайдеров;
- юридическая проверка коммерческого использования моделей;
- политика хранения и удаления пользовательских данных.
