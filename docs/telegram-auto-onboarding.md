# Telegram: подключение без ручных ключей

## Как теперь работает продукт

**По приглашению:** владелец выбирает тариф в «Telegram» → «Создать приглашение».
Человек открывает ссылку и нажимает Start. Шлюз сам создаёт аккаунт, привязывает
Telegram ID, назначает тариф и выдаёт внутреннюю сессию. Редактировать JSON,
копировать ID или создавать персональные API-ключи не нужно.

**Без приглашения:** Start автоматически создаёт заявку. Владелец нажимает
«Разрешить доступ» в админке. Человек нажимает «Проверить доступ» в боте или просто
пишет следующее сообщение. Это сохраняет закрытую бету: решение, кого допустить,
не заменено безлимитной публичной регистрацией за счёт владельца.

Приглашение одноразовое и действует 24 часа. Его можно отозвать в панели.
Перезапуск, повторный Start и повторное открытие ссылки не создают второй аккаунт,
не обнуляют расход и не назначают подписку повторно. Действующий тариф существующего
аккаунта сохраняется; для его изменения используется обычное управление тарифами.

## Обновление уже настроенного бота: выполняет Codex/разработчик

1. Сохранить несохранённые локальные правки Codex, `.env.owner`, `.env.telegram`,
   старый файл доступа и согласованную резервную копию баз. Не удалять Docker-тома.
2. Обновить код ветки `implementation/telegram-beta-complete`. Не использовать main,
   пока PR не объединён. Не затирать локальные изменения без сравнения самим агентом.
3. Обновить оба компонента вместе одной командой:

```sh
docker compose -p shluz-owner-check --env-file .env.owner -f compose.owner.yaml -f compose.owner.telegram.yaml up -d --build --wait
```

Шлюз сам создаёт служебный ключ в новом Docker-томе `owner_telegram_connector`.
Бот видит его только для чтения. Старые `owner_data` и `owner_telegram_data`
сохраняются. `.env.telegram` уже содержит токен BotFather — повторно вводить его не нужно.
Добавлена миграция БД шлюза `20261018_06`, она создаёт новые таблицы, не меняет старые данные.
База истории бота остаётся версии 2.

**Старый `telegram-access.json` необязателен.** Если там уже есть действующий ключ,
бот при первом сообщении автоматически переносит доступ в шлюз, сохраняя аккаунт,
назначенное владельцем имя, тариф, квоту и связь с локальной историей. Отозванные
ключи не восстанавливаются. Шлюз продолжает учитывать отзыв импортированного ключа.
После явного восстановления доступа через панель старый ключ уже не используется.
`TELEGRAM_ACCESS_FILE_HOST`, если был установлен, поддерживается для старого файла;
по умолчанию читается только `telegram-access.json` из каталога `secrets`.
Не складывать другие секреты в этот каталог: он монтируется боту только для чтения.
При отсутствии каталога Docker создаёт пустой — никакого файла на пользователя не нужно.

После миграции источник разрешений — раздел **Telegram** в шлюзе. Удаление строки
из старого JSON больше не является отзывом: используйте «Закрыть доступ» в админке.
Кнопка закрывает и уже выданные короткие сессии. Архивирование аккаунта также закрывает вход.

Для обычного, не owner, контура применяется `docker compose --profile telegram up -d --build --wait`.
Не заменять owner-контур обычным — это другая конфигурация базы и портов.

## Что остаётся однократной настройкой

Создать своего бота и передать его секрет хостингу необходимо один раз. Это делает
владелец в защищённом интерфейсе или локальный Codex с его разрешения. BotFather-токен
принадлежит всему боту, а не отдельному пользователю. Это не этап регистрации каждого человека.
Настоящие ключи не включаются в репозиторий и не отправляются в переписку.

## Границы доверия

- `/internal/telegram/hello` и `/internal/telegram/session` требуют отдельный случайный
  служебный ключ. Обычные клиентские и bootstrap-токены там не подходят.
- Это доверенный серверный канал, **не публичная авторизация по произвольному Telegram ID**.
  Только бот принимает ID из проверенного Telegram update в личном чате; не из текста пользователя.
  За пределами закрытой Docker-сети соединение должно использовать HTTPS.
- Новые сессии подписаны HMAC-SHA256 и действуют 15 минут. Для каждого запроса шлюз
  дополнительно проверяет разрешение, привязку, версию сессии и статус аккаунта в БД.
  Бот не хранит персональные токены в пользовательских файлах или истории и не получает admin-key.
- Приглашения хранятся только в виде хеша. Полная ссылка показывается один раз.
- Все расходы и квоты остаются в прежнем UsageService. Отдельные тарифы Telegram/desktop
  не включаются скрытно этим обновлением. Одобрение — не подтверждение оплаты.
- Создание/одобрение заявок сериализовано: BEGIN IMMEDIATE для SQLite, advisory transaction
  lock для PostgreSQL. Это небольшие транзакции закрытой беты, не блокировка генерации модели.
- Очередь новых заявок ограничена (по умолчанию 500). Нет внешних платных вызовов при регистрации.
- Компрометация служебного ключа позволяет имитировать Telegram-клиент: хранить том на
  защищённом сервере, не публиковать и не использовать его для других интеграций.

## Проверки разработчика

`tests/api/test_telegram_onboarding.py`: заявки, приглашения, повтор и гонки, подмена ID,
истечение и отзыв сессии, архив/восстановление, миграция старого доступа, сохранение квот,
CSRF, отсутствие ключей в ошибках, ограничение очереди.
`tests/telegram/test_bot.py`: настоящий dispatcher → FastAPI → mock без JSON на пользователя.
`tests/telegram/test_runtime.py`: опциональный старый файл, BOM, редактирование секретов,
настройка автоматического режима в Compose.
Браузерная проверка — в `ui_tests`; PostgreSQL и контейнерная проверка — в CI.
Тесты не обращаются к настоящему Telegram или платным моделям.

Опубликованный код не равен установке у владельца: локальную сборку/перезапуск выполняет
агент с доступом к компьютеру. После установки владелец только открывает бота и оценивает UI.
