# Shluz: база пользователей и учёта

**Дата:** 2026-09-29  
**Статус:** согласовано для реализации

## Назначение

Добавить постоянный слой данных, который станет единым источником правды о пользователях, способах входа, ролях, тарифах, подписках, API-токенах и фактическом расходе нейросетей.

## Зафиксированные решения

- Приложение остаётся модульным монолитом.
- Для доступа к данным используется SQLAlchemy 2.
- Локальный режим по умолчанию использует SQLite, чтобы сервис запускался одной командой и без отдельной базы.
- Рабочий сервер может использовать PostgreSQL или Supabase заменой одной переменной `SHLUZ_DATABASE_URL`.
- Таблицы создаются автоматически при запуске на этом этапе; SQL-миграция для Supabase хранится в репозитории отдельно.
- Секретные значения API-токенов и ключей провайдеров никогда не хранятся в открытом виде.
- Интерфейс администратора сначала только показывает данные; редактирование будет добавляться отдельными безопасными формами.
- До появления персональных токенов запросы учитываются как системные, но уже с каналом, моделью, токенами, себестоимостью и статусом.

## Сущности

### accounts

Единый пользователь Shluz. Содержит статус, роль, отображаемое имя и даты создания/изменения.

### identities

Способы входа и внешние идентификаторы: email, Telegram, Supabase Auth и будущие каналы. Несколько identities могут принадлежать одному account.

### plans

Тарифы сервиса: код, название, валюта, цена, включённые внутренние кредиты и статус активности.

### subscriptions

Связь пользователя с тарифом, статус подписки и период действия.

### api_tokens

Метаданные пользовательских ключей Shluz: префикс, хэш, права, срок действия и последнее использование. Полное значение ключа после создания не сохраняется.

### usage_events

Каждый вызов модели: пользователь (если известен), канал, провайдер, модель, количество входных/выходных токенов, закупочная стоимость, списанные внутренние кредиты, статус и код ошибки.

### audit_events

Административные действия: кто, что, над каким объектом и когда изменил.

## Учёт запроса

1. До платного вызова создаётся событие со статусом `pending`.
2. Если база недоступна, внешний провайдер не вызывается — это предотвращает неучтённые расходы.
3. После успешного ответа событие получает токены, стоимость и статус `succeeded`.
4. При ошибке провайдера событие получает статус `failed` и безопасный код ошибки.
5. Если финальная запись временно не удалась, ответ пользователю не повторяется автоматически, чтобы не вызвать двойное списание у провайдера; ошибка фиксируется в журнале сервера.

## Визуальная панель

Добавляются страницы:

- `/admin/users` — пользователи, роли, статусы, способы входа и расход;
- `/admin/plans` — тарифы и подписки;
- `/admin/usage` — общая стоимость, токены, запросы, ошибки и последние события;
- `/admin/tokens` — метаданные клиентских токенов без секретов;
- главная `/admin` получает ссылки и сводные показатели.

Пустые таблицы должны объяснять, какой следующий шаг заполнит данные, а не выглядеть как ошибка.

## Безопасность

- Ключ Venice остаётся только в Secrets/`.env`.
- Пользовательские API-токены в базе хранятся только как криптографический хэш и безопасный префикс.
- Supabase-миграция включает RLS для пользовательских таблиц без публичных политик; прямой доступ клиентов по умолчанию запрещён.
- Админ-панель остаётся закрытой отдельной авторизацией.
- Денежные значения хранятся как Decimal/Numeric, а не float.

## Граница этапа

Входит:

- схема данных;
- SQLite/PostgreSQL-совместимый слой;
- учёт всех API-запросов;
- визуальные страницы администратора;
- Supabase SQL-миграция;
- тесты и документация.

Не входит:

- публичная регистрация;
- вход через Telegram или email;
- выпуск персональных токенов через интерфейс;
- редактирование тарифов;
- приём платежей;
- применение миграции к неактивному Supabase-проекту без отдельного подтверждения владельца.
