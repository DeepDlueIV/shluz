# Shluz: архитектура центрального API-шлюза

**Дата:** 2026-09-29  
**Статус:** согласовано для начальной реализации

## 1. Назначение

Shluz — единая серверная точка между пользовательскими каналами и поставщиками нейросетей.

```text
Harness / сайт / Telegram
          ↓
        Shluz
          ↓
Venice / Nous / OpenRouter / собственные модели
```

Пользовательские приложения не должны знать реальные ключи, внутренние цены и устройство провайдеров. Они работают только с API Shluz.

## 2. Основные цели

1. Один API для Harness, сайта и Telegram.
2. Возможность менять поставщика моделей без переделки клиентов.
3. Централизованный учёт пользователей, тарифов, лимитов и расходов.
4. Визуальное управление системой через браузер.
5. Простое развёртывание и перенос на другой сервер.
6. Безопасное хранение ключей поставщиков только на сервере.
7. Возможность постепенно добавлять текст, изображения, аудио и другие функции.

## 3. Архитектурный подход

На старте используется **модульный монолит**: одно серверное приложение, внутри которого части отделены понятными интерфейсами.

Это проще и надёжнее микросервисов на ранней стадии, но не мешает позднее вынести отдельные части в самостоятельные сервисы.

```text
Shluz
├── Public API
│   ├── /v1/models
│   ├── /v1/chat/completions
│   └── позднее /v1/images/generations
├── Авторизация и лимиты
├── Маршрутизация моделей
├── Адаптеры провайдеров
├── Учёт использования
├── Визуальная админ-панель
├── Аудит и журнал ошибок
└── База данных
```

## 4. Публичный контракт

Внешний API по возможности совместим с OpenAI API. Это позволит подключать разные Harness-клиенты и библиотеки без специальных доработок.

Первая версия поддерживает:

- `GET /health` — состояние сервиса;
- `GET /v1/models` — доступные модели;
- `POST /v1/chat/completions` — текстовый диалог;
- `/docs` — интерактивная документация API.

Позднее добавляются:

- `POST /v1/images/generations`;
- потоковые ответы;
- загрузка файлов;
- мультимодальные сообщения;
- аудио и видео при необходимости.

## 5. Адаптеры провайдеров

Каждый поставщик подключается отдельным адаптером с одинаковым внутренним интерфейсом.

```text
ProviderAdapter
├── list_models()
├── chat_completion()
└── позднее generate_image()
```

Первая версия использует `MockProvider`, который не обращается во внешний интернет. Следующим адаптером будет Venice.

Клиенты не должны зависеть от названий и форматов конкретного поставщика.

## 6. Пользователи и данные

Будущая база данных содержит следующие основные сущности:

- `accounts` — единый пользователь;
- `identities` — способы входа: email, Telegram и другие;
- `plans` — тарифы;
- `subscriptions` — активные подписки;
- `balances` и `quotas` — доступный объём использования;
- `usage_events` — фактические расходы;
- `providers` — подключённые поставщики;
- `models` — доступные модели и правила маршрутизации;
- `api_tokens` — токены клиентов Shluz;
- `audit_events` — административные действия.

Supabase рассматривается как удобный управляемый PostgreSQL и сервис авторизации, но код не должен быть намертво привязан к нему. Основная база — стандартный PostgreSQL.

## 7. Визуальное управление

Вместе с API создаётся закрытая браузерная админ-панель.

Первая версия показывает:

- состояние сервиса;
- активных провайдеров;
- количество моделей;
- ссылки на документацию;
- безопасное отображение конфигурации без секретов.

В дальнейшем добавляются разделы:

- пользователи;
- тарифы и подписки;
- баланс и расход;
- провайдеры и модели;
- ошибки и аудит;
- состояние очередей и внешних API.

Для первой версии используется серверный HTML с Jinja2 и небольшим количеством HTMX. Это не требует отдельного frontend-проекта и остаётся лёгким.

## 8. Безопасность

Обязательные правила:

1. Ключи Venice и других поставщиков никогда не передаются в Harness, сайт или Telegram.
2. Секреты не хранятся в GitHub и не записываются в логи.
3. Конфигурация передаётся через переменные окружения или secret manager хостинга.
4. Админ-панель всегда защищена отдельной авторизацией.
5. Пользовательские токены отличаются от ключей поставщиков.
6. В production используется только HTTPS.
7. Для запросов применяются лимиты, таймауты и контроль максимальной стоимости.
8. Административные действия позднее записываются в аудит.

Docker-контейнер обеспечивает переносимость и изоляцию процесса, но не является хранилищем секретов.

## 9. Переносимость

Сервис должен запускаться одинаково:

- локально на Windows для разработки;
- в Docker на Linux-сервере;
- на любом хостинге, поддерживающем контейнеры;
- с Supabase либо с обычным PostgreSQL.

Все внешние зависимости и адреса задаются конфигурацией. Замена Venice на другого поставщика не меняет публичный API Shluz.

## 10. Этапы разработки

### Этап 1 — переносимый фундамент

- модульная структура FastAPI;
- конфигурация через окружение;
- `MockProvider`;
- `/v1/models` и `/v1/chat/completions`;
- временный серверный API-токен;
- закрытая минимальная админ-панель;
- Docker;
- тесты и GitHub Actions;
- понятная документация.

### Этап 2 — реальный провайдер

- Venice API;
- потоковая выдача ответа;
- таймауты, повторные попытки и нормализация ошибок;
- учёт реального расхода провайдера;
- генерация изображений через отдельный API-метод.

### Этап 3 — пользователи и база

- PostgreSQL/Supabase;
- единые аккаунты и связанные идентификаторы;
- вход через сайт и привязка Telegram;
- пользовательские токены;
- аудит.

### Этап 4 — тарифы и расчёты

- тарифы;
- подписки;
- лимиты;
- внутренние кредиты;
- отчёты по себестоимости и марже;
- блокировка перерасхода.

### Этап 5 — пользовательские каналы

- Harness;
- Telegram-бот;
- демонстрационный сайт;
- личный кабинет пользователя.

## 11. Что намеренно не входит в первый этап

- платежи;
- полноценная регистрация пользователей;
- Supabase;
- реальный Venice API;
- локальные модели;
- очередь фоновых задач;
- микросервисы;
- сложный frontend;
- окончательный выбор Harness.

Эти функции добавляются после того, как фундамент становится тестируемым и переносимым.

## 12. Зафиксированные решения

- Архитектура начинается с модульного монолита.
- Публичный API остаётся провайдер-независимым.
- Основной контракт совместим с OpenAI API.
- Управление доступно через браузер, а не только через терминал.
- Supabase является опцией, а не обязательной зависимостью.
- Первым реальным провайдером планируется Venice, но система не привязывается к нему.
- Все изменения проходят через отдельную ветку, тесты и pull request.
