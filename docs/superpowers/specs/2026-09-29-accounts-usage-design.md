# Shluz: пользователи, тарифы и учёт расходов

**Дата:** 2026-09-29  
**Статус:** согласовано для реализации

## Цель

Добавить постоянную базу данных и визуальный административный слой, в котором владелец видит пользователей, способы входа, тарифы, подписки, токены доступа и расход по каждому запросу.

## Архитектурное решение

- База приложения остаётся обычным PostgreSQL, чтобы проект не зависел от одного сервиса.
- Supabase используется как удобный управляемый PostgreSQL и позднее как источник пользовательской авторизации.
- Для локального запуска по умолчанию используется SQLite-файл; переход на PostgreSQL выполняется одной переменной окружения.
- Доступ к данным из кода идёт через SQLAlchemy.
- На этом этапе текущий общий Bearer-токен относится к технической учётной записи `bootstrap`; персональные токены появятся следующим шагом.

## Основные сущности

- `accounts` — единый пользователь или техническая учётная запись;
- `identities` — способы входа: email, Telegram и другие;
- `plans` — тарифы и лимиты;
- `subscriptions` — подписка пользователя на тариф;
- `api_tokens` — будущие персональные токены Shluz; в базе хранится только хэш;
- `usage_events` — каждый запрос, модель, токены, себестоимость провайдера, статус и источник.

## Визуальное управление

Закрытая панель получает разделы:

- `/admin/users` — пользователи, роли, статус, способы входа и подписка;
- `/admin/plans` — тарифы и установленные лимиты;
- `/admin/usage` — общая себестоимость, токены, запросы и детализация по пользователям, моделям и каналам;
- главная `/admin` — ссылки и ключевые показатели.

На первом шаге разделы предназначены для просмотра. Безопасное редактирование пользователей и тарифов будет добавлено отдельно, после стабилизации схемы.

## Учёт запросов

После успешного ответа провайдера Shluz сохраняет:

- внутренний ID пользователя;
- источник (`harness`, `site`, `telegram`, `bootstrap`);
- поставщика и модель;
- ID запроса поставщика;
- входные и выходные токены;
- себестоимость в USD и DIEM;
- время и статус.

До появления персональной авторизации запросы записываются на техническую учётную запись `bootstrap`.

## Безопасность

- реальные токены пользователей и ключи поставщиков в базе не хранятся в открытом виде;
- административные страницы остаются под отдельной авторизацией;
- публичный API не раскрывает себестоимость и внутренние данные;
- соединение с PostgreSQL задаётся только серверной переменной окружения;
- секреты не попадают в GitHub и браузер.

## Supabase

Подключённый проект Supabase сейчас находится в состоянии `INACTIVE`. Код и схема готовятся без изменения удалённого проекта. Восстановление проекта и применение миграции выполняются отдельно после явного подтверждения владельца, поскольку это внешнее действие и может влиять на тариф или ресурсы.

## Граница этапа

В этот этап не входят:

- самостоятельная регистрация конечного пользователя;
- вход через Telegram или email;
- платежи;
- автоматическое списание внутренних кредитов;
- редактирование данных из административной панели;
- хранение содержимого пользовательских запросов.

Эти функции опираются на создаваемую сейчас базу и будут добавляться следующими отдельными этапами.
