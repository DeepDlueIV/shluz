# Контракт Telegram ↔ Shluz

Версия клиента: закрытая бета, 2026-10-01. Все запросы к шлюзу идут по HTTP
в закрытой сети Compose; для удалённого подключения используйте HTTPS.

## Ответственность компонентов

`app/`: аккаунты, identities, подписки, токены, модели, квоты и учёт расхода.
`telegram_bot/`: закрытый список Telegram ID → отдельный персональный токен,
локальные настройки/история, UI, доставка ответа и защита от повторов updates.
Бот не читает БД шлюза и не вызывает поставщиков моделей напрямую.

## Аутентификация и endpoints

`Authorization: Bearer shluz_...` — отдельный персональный токен канала `telegram`
на пользователя. Нельзя передавать bootstrap-токен вместо персонального.

- `GET /v1/me`: личный аккаунт, текущий эффективный тариф и доступные квоты.
  Новая операция; `Cache-Control: no-store`; без себестоимости, хешей токенов,
  чужих аккаунтов, маржи, данных админки. Без входа 401, bootstrap 403.
- `POST /v1/me/telegram`: доверенный сервер бота передаёт
  `{"telegram_id":123456789,"username":"optional"}` после получения Telegram update.
  Операция доступна только персональному токену канала `telegram`, повторная привязка
  того же ID/аккаунта безопасна. Несовпадение аккаунта — 409, другой канал — 403,
  нецелый/неположительный ID — 422. Ответ: `{"account_id":"...","telegram_id":123456789}`.
  Это **не** публичный Telegram Login/проверка подписанной авторизации Telegram.
  Бот — доверенный посредник, а локальный файл доступа задаётся администратором.
- `GET /v1/models`: существующий OpenAI-подобный `{"data":[{"id":"mock-chat",...}]}`.
  Бот получает список заново при выборе модели и перед генерацией.
- `POST /v1/chat/completions`: существующий текстовый API;
  `{"model":"mock-chat","messages":[{"role":"user","content":"Привет"}],"stream":false}`.
  Ответ читается из `choices[0].message.content`. UI ожидания не притворяется
  настоящим streaming: потоковая генерация шлюза здесь не реализуется.

Форма `/v1/me`:
```json
{
  "account": {"id": "account-id", "display_name": "Тестировщик", "status": "active"},
  "channel": "telegram",
  "plan": {"id": "plan-id", "code": "beta", "name": "Бета", "scope": "account", "ends_at": null},
  "allowance": {
    "scope": "account",
    "resets_at": "2026-11-01T00:00:00+00:00",
    "requests": {"limit": 100, "used": 3, "pending": 1, "remaining": 96},
    "credits": {"limit": null, "used": 0, "pending": 0, "remaining": null}
  }
}
```
Числа/дата в примере иллюстративные. `plan:null` означает отсутствие активного тарифа,
а не бесплатный доступ. Нулевая/неустановленная квота текущего шлюза представлена
`limit:null`: неограничен только этот показатель, другие ограничения продолжают действовать.
В расчёт входят успешные запросы и неистёкшие резервы с начала текущего месяца UTC.
Правило выбора активной подписки соответствует существующему UsageService.

## Ошибки и неопределённый результат

Коды `subscription_required`, `credit_limit_exceeded`, `request_limit_exceeded`,
`spend_limit_exceeded`, `model_not_found`, `provider_rate_limit` переводятся в понятные
экраны. Общие 401/403/409/422 и ошибки сети обработаны отдельно. Детали провайдера,
секреты и traceback пользователю не показываются.

X-Request-ID — идентификатор локального запроса для корреляции, **не** ключ
идемпотентности. Бот не повторяет POST генерации. Durable processed_updates и turns
уменьшают риск повторного расхода. Не подтверждённый после перезапуска запрос получает
статус `unknown`, не отправляется снова и не попадает в контекст успешного диалога.
Повторная попытка, вручную отправленная пользователем, является новым запросом.
Технические отметки processed_updates очищаются через 7 дней; идентификатор генерации
также уникален в сохранённых turns. Это не платформа гарантированной доставки очередей.

Ответ фиксируется в истории **до** отправки Telegram. Ошибка доставки или отмена
показа не уничтожает уже сохранённый ответ. Ошибка сети/некорректный ответ после POST
не доказывают, что расход отсутствовал. Отмена ожидания не равна возврату средств.

## Расширения позже

Отдельные права/тарифы/квоты по каналам проектируются в шлюзе и отражаются через
`scope`/новые поля. Текущий контракт честно возвращает `scope:account` и не обещает
независимые остатки desktop/Telegram. Платежей и выбора окончательного провайдера
в этом этапе нет; API-клиент не зависит от Venice или собственного GPU.
