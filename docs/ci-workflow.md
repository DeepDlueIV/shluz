# Проверки веб-правок без повторной полной сборки

## Рабочий порядок

1. Создать рабочую ветку и **Draft PR** в `main`. До PR автоматические веб-проверки ветки не запускаются.
2. Во время исправлений запускать локально нужный test-файл или браузерный сценарий. В Draft PR CI выполняет только `npm ci`, unit-тесты, проверку типов и тесты маршрутизации CI — без Chromium и production build.
3. Когда правка закончена, перевести PR в **Ready for review**. Это запускает полную сборку и все шесть существующих браузерных сценариев/скриптов. Проверить именно текущую версию PR, а не старый зелёный результат.
4. После успешного полного прогона объединить PR. Если после проверки меняется код, Ready PR снова проверяется полностью. Для следующего цикла отладки сначала вернуть PR в Draft.
5. В `main` остаётся быстрая контрольная проверка; полные браузерные тесты после merge не повторяются. Публикация остаётся за существующей Git-интеграцией Vercel. Не делать дополнительный ручной деплой.

Зелёный Draft/Quick **не означает** прохождение браузерных тестов и не разрешает пропуск полного прогона перед merge. Правила защиты ветки этим изменением не настраиваются.

## Ручной запуск и адресная диагностика

В Actions → Web checks → Run workflow доступны `quick` и `full`. По умолчанию `full`. Такой запуск полезен для ветки без PR или повторной диагностики; не запускать его параллельно уже работающему автоматическому прогону той же версии.

Пример локальных быстрых проверок из `web/` (Node 24):

```sh
node --experimental-strip-types --test --test-isolation=none src/lib/home-reload.test.ts
npm run typecheck
```

После production build и запуска локального сервера достаточно адресного браузерного скрипта, например `node scripts/scroll-reload-check.mjs` для прокрутки или `node scripts/hover-continuity-check.mjs` для наведения. Для полного прогона перед merge CI по-прежнему запускает все скрипты. Не сокращать сами тесты и не удалять проверки ради зелёного результата.

## Что экономит время

- Рабочие push не дублируют PR-прогоны. Быстрые и полные запуски одного PR используют общую группу concurrency; новая версия отменяет устаревшую.
- Backend/Docker остаётся без изменений по составу проверок, но не запускается для доказанно веб-only diff. Изменения общих файлов, смешанные правки и неизвестный/недоступный diff требуют backend CI. Проверка `test` сохраняется как явно skipped для web-only, а ошибка определения области не маскируется успехом.
- Исходный архив больше не создаётся на каждом push. Он доступен по отдельной опции `export_source` ручного запуска; исключены node_modules, .next, результаты и .env-файлы. Скриншоты/JSON полного прогона сохраняются как раньше.
- Установка Playwright и выполнение тестов разделены на два шага, чтобы измерять их независимо. Браузерные тесты остаются последовательными: параллельная нагрузка может искажать проверки промежуточных кадров анимации.

## Как оценивать выигрыш

Сравнивать `started_at` / `completed_at` у job и отдельных steps, отдельно от очереди. Главный выигрыш — отсутствие полного прогона на каждой промежуточной правке, а не гарантированное ускорение самого финального браузерного набора. Длительность анализа/редактирования ассистентом в эти цифры не входит.
